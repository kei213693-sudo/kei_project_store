This is a OTA device firmware update profile for update APP, Patch and patch, which compatible Nordic app.

Overview

This is a OTA(Over the air) device firmware update profile for update APP, Patch and patch.

  • Connection with the device through the mobile APP, and update the device application, patch or configuration through the BLE
  • Using sha256 and ECDSA secp256r1 algorithm to ensure data integrity

Flash layout

          |                                       |
          |                ......                 |
          |                                       |

Generate OTA firmware

Tool: pc-nrfutil.exe v3.5.1
This application is used to package image files. Nordic supports three types of files, namely application,
softdevice, and bootloader. When the device performs DFU, multiple types can be updated simultaneously.
The files we can package are also divided into three types, which are application, patch, Configuration.
The corresponding relationship of Nordic as follows:

Nordic OnMicro
Application Configuration
Bootloader Patch
SoftDevice Application

Although two or three types of data can be updated at the same time, not all combinations are supported.
Specific combinations supported can be viewed through 'nrfutil pkg generate –help'.
In the parameters, the version information parameters such as –hw-version are required.
These information are used for the user to judge the substitutability between versions when performing
DFU on the device side.

Note
We do not detect version information during the upgrade process

DFU function realization process:

  1. Download nrfutil.exe and add the path to Environment Variables
  2. If no private key has been generated, use the command 'nrfutil keys generate private-key.pem' to generate
    a private key. The private key private-key.pem must be kept by yourself.
    Then use the command 'nrfutil keys display private-key.pem –key pk –format code –out_file key.c' to generate
    the public key file key.c, copy the public key in key.c to the variable dfu_public_key in dfu_public_key.c
  3. Modify dfu_version in the dfu_version.c file to the required version string.
    Note: The DFU Service currently has Characteristic with a UUID of 0x0003, which is used to read the current
    APP version information. This function is compatible with Nordic DFU but is not required.
  4. Compile the program and generate the nrf51422_xxac_s110.bin file under ble_app_nordic_dfu,
    which is the burn file of the APP

  5. Package files
    The recommended combination of packaged burning files is APP, APP + Patch and APP + Patch + Config.

    • Prepare the burning file (app.bin, patch.bin, config.bin) and secret key file (private-key.pem)
    • Use the nrfutil tool to package the bin file. Since we did not use the version information in
      the nrfutil tool, the version information in the parameters has no practical significance.
    • Package app.bin:
      nrfutil pkg generate –key-file private-key.pem –hw-version 0 \
      –softdevice app.bin –sd-id 0 –sd-req 0 firmware.zip
    • Package app.bin + patch.bin:
      nrfutil pkg generate –key-file private-key.pem –hw-version 0 \
      –bootloader patch.bin –bootloader-version 0 –softdevice app.bin –sd- id 0 –sd-req 0 firmware.zip
    • Package app.bin + patch.bin + cfg.bin:
      nrfutil pkg generate –key-file private-key.pem –hw-version 0 \
      –application cfg.bin –application-version 0 –bootloader patch.bin \
      –bootloader-version 0 –softdevice app.bin –sd-id 0 –sd-req 0 firmware.zip

    After successful packaging, The compressed package firmware.zip is generated.

  6. Modify the firmware.zip file name to the required file name (if the mobile terminal upgrade program
    needs to burn the file version information, it can only be obtained by the file name, the version
    information in app.bin can't be read)
  7. Send the burning compression package to the mobile phone. Connect the phone to the device, and obtain
    and display the version information of the burning compression package and the device if necessary
    (Nordic official APP does not have the function of obtaining version information)

  8. Start DFU prcedure and confirm the upgrade on the mobile phone. Wait for the upgrade to complete.
    Note that if there is both APP and Config in the burning compressed package, Bluetooth will be disconnected
    after the burning of the APP is completed and the Config will be burned after reconnecting
    (APP and patch are always burned at the same time)

Reference Protocol

GATT Service

The UUID for the Secure DFU Service is 0xFE59. The service must be instantiated as a primary service.
The following characteristics are mandatory

Characteristic name Required properties UUID
DFU Control Point Write, Notify 0x8EC90001-F315-4F60-9FB8-838830DAEA50
DFU Packet WriteWithoutResponse, Notify 0x8EC90002-F315-4F60-9FB8-838830DAEA50
Image Version Read 0x0003
  • DFU Control Point
    The UUID of the DFU Control Point characteristic is 0x0001.
    The DFU Control Point characteristic is used to control the state of the DFU process. All DFU procedures are
    requested by writing to this characteristic. A response that marks the end of the procedure is received as a notification.
  • DFU Packet
    The UUID of the DFU Packet characteristic is 0x0002. This characteristic receives data for Device Firmware
    Updates as DFU packets.
  • Image Version
    The UUID of the Image Version characteristic is 0x0003. Device version, the format of version is user defined.

Message sequence charts

The following message sequence charts show the transfer of an init packet and a firmware image, respectively.

Transfer of an init packet

The DFU controller first checks if the init packet has already been transferred successfully. If not,
the DFU controller checks if it has been transferred partially. If some data has been transferred already,
the transfer is continued. Otherwise, the DFU controller sends a Create command to create a new data object
and then transfers the init packet. When the init packet is available, the DFU controller issues an Execute
command to initiate the validation of the init packet.

Transfer of a firmware image

  • A firmware image is split up into several data objects that are transferred consecutively. If the transfer of
    a data object fails (for example, because of a power loss), the transfer can be continued instead of restarted.
    Therefore, the DFU controller starts by selecting the last data object that was sent and checks if it is
    complete and valid. If it is, the controller issues an Execute command and then continues the transfer with
    the next data object. Otherwise, the DFU controller sends a Create command to create a new data object if
    required (thus if the transfer for this data object has not started yet or the received data is corrupted)
    and then transfers the next data object.
  • When all packets are transferred, the DFU controller issues an Execute command to trigger the actual
    firmware update.
  • The DFU controller is responsible for keeping track of the progress. The response to each Select command
    contains information about the maximum object size, the current offset, and the CRC. For example, if the
    image size is 10 kB and the maximum object size is 4 kB, 3 data objects must be transferred. If the
    returned offset is 6 kB, the DFU controller knows that the current object is the second object to
    transfer and that is has not been transferred completely.

Other considerations

  • Related data of sha256 and secp256r1, including private key, public key, hash value and digital signature
    are stored in little endian format.
  • Signature verification can only guarantee that the burned files and parameters have not been tampered
    with or forged, but the data is not encrypted.

Examples of nrfutil commands:

  • Generate a key pair and save it to the private-key.pem file
    nrfutil keys generate private-key.pem
  • Extract the public key from the private-key.pem file and generate the code to dfu_public_key.c
    nrfutil keys display private-key.pem –key pk –format code –out_file dfu_public_key.c
  • Use private-key.pem to package cfg.bin, patch.bin and app.bin to generate the file fw_p_a_c.zip
    nrfutil pkg generate –key-file private-key.pem –hw-version 0x0d –application cfg.bin \
    –application-version 0x0a –bootloader patch.bin –bootloader-version 0x0b \
    –softdevice app.bin –sd-id 0x05 –sd-req 0x10,0x20,0x30 fw_p_a_c.zip
